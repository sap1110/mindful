Working directory: /workspace/mindful
This is a persistent project directory and a git repository — your earlier work
here is preserved across runs, so build on it (pass `resume` to continue a prior
run in this same tree). New, unrelated work belongs in its own project directory:
pass a project name as the workdir. If you find loose work sitting outside a
project, move it into one. Keep each project as its own git repo.

This machine restarts often between runs. The filesystem survives those
restarts, but /tmp, /run, and /dev/shm are wiped every time — so never point a
server, service, or later run at a file under those paths. Anything that must
be readable again (config, key files, data) belongs in the project tree.

Commit with git regularly as you go, not just at the end — small, frequent commits
let you inspect state and roll back a bad change with git instead of losing
progress. Point your verify command at the same paths you actually write to.

Rules: implement fully. Write the files, do not stop at a plan. For a large
file, build it up in steps (create it, then append/edit) rather than emitting the
whole thing in one enormous write — a single very large generation can stall or
be cut off mid-stream, losing all of it.

You have network access and a package manager. If the job wants a tool, a CLI or
a library you do not have yet, install it: `npm i`, `npx <tool>`, `pip install`,
`curl` a file, clone a repo. A component registry like shadcn is a normal
`npx shadcn@latest add ...` away. Do not treat a missing tool as a constraint
to design around, and do not hand-reimplement something you could install.

The same goes for READING. Any URL in your brief is a source to open, not
decoration: a design system, a component registry, a style guide, an API
reference, a spec, or just a site whose look you have been asked to match.
`curl` it and work from what it actually says. Values quoted in the brief
alongside a URL are the operator's recollection, so where the two disagree the
fetched page wins. This matters most for a visual brief, where "match this
design language" is not something you can approximate from memory: fetch the
tokens, the theme file, the component source, and use the real colours, fonts,
spacing and radii rather than a plausible-looking palette of your own. If a
page will not load, say so instead of filling the gap.

If your brief says a tool is unavailable or a framework is unsupported, treat
that as the operator's assumption and check it. It is often wrong, and it is
the expensive kind of wrong: a run once hand-ported a design system because its
brief said the CLI could not be used, then a second run installed the very same
packages in the very same sandbox fifteen minutes later. Try the install; if it
genuinely fails, say what failed rather than quietly building the workaround.

Size your checking to the job, and MINIMISE BUILD/VERIFY ROUND TRIPS. A full
build-and-verify chain (typecheck + bundle + boot a server + replay a scenario)
costs minutes of the owner's wait every single time, and has no incremental mode,
so each extra round trip is among the most expensive things you can choose to do.
Measured on real runs: one spent 518 seconds on three `npm run verify` calls —
74% of its working time — for one deliverable.

- Judge the work first. A copy edit, a colour change or a config tweak needs no
  build. A new dependency, a type-level change or a new route does. Check at the
  level the change actually warrants.
- Prefer the cheapest check that would catch the mistake you might have made:
  read the file back, or typecheck the single file, before reaching for the whole
  chain. A full verify is a closing step, not a habit between edits.
- Batch the edits, then verify ONCE. If a verify fails, fix everything it
  reported before running it again — never re-run the chain to watch one error at
  a time.
- Never re-run an identical verify to confirm a result you already have. Two
  consecutive green verifies means the second was wasted.

Build Phase 1 of "Mindful", a mental-health companion web app targeting the Best Design track of the Hack for Humanity hackathon. The project scaffold already exists at /workspace/mindful (Vite 6 + React 18.3 + TypeScript 5.6 + Tailwind v3.4 + ESLint 9). framer-motion and react-router-dom are already installed.

GOAL for this phase (per the locked plan): lock the visual identity early with a clean, calming design system, and build a lightweight auth + 3-screen onboarding flow that sets the design tone immediately.

WHAT TO BUILD:

1. DESIGN SYSTEM (the primary differentiator - we're targeting Best Design):
   - Extend tailwind.config.js with a calming mental-health palette: soft, muted, low-saturation colors (e.g. sage/teal/lavender/cream/off-white base, one calm accent). Define semantic tokens: background, surface, primary, accent, text, muted, border, success.
   - Set up typography: a clean, friendly font pairing (e.g. a serif display for headings + a sans for body, loaded from Google Fonts via index.html or CSS @import). Define type scale.
   - Define spacing scale and rounded corners (soft, friendly radii).
   - src/index.css: base styles, CSS variables for the tokens, smooth transitions, calm global feel.
   - A reusable design-token file (e.g. src/theme.ts) exporting the palette/type/spacing constants so components stay consistent.

2. AUTH + ONBOARDING FLOW (lightweight, on-device - data stays on-device per the safety rules):
   - A landing/welcome screen that's the design showpiece: calm, accessible, with a clear "Get started" entry.
   - A 3-screen onboarding flow: (1) name, (2) "what brings you here" (multi-select of reasons), (3) "preferred coping style" (choose one). Use framer-motion for smooth screen transitions (micro-interactions are design points).
   - Store the completed profile in localStorage (on-device). After onboarding, show a simple "You're all set" completion state with a disclaimer that this is not medical advice (mandatory disclaimer per plan).
   - A minimal auth gate: if a profile exists in localStorage, skip onboarding and show the "home" placeholder; if not, show onboarding. Keep it simple - no real backend auth needed for this phase (plan allows lightweight/on-device).

3. ROUTING: use react-router-dom with routes for / (landing), /onboarding (the 3-step flow), and a /home placeholder after completion.

4. ACCESSIBILITY (WCAG AA is a judging criterion): semantic HTML, proper labels on all inputs, focus states, sufficient color contrast, keyboard navigable, aria attributes where needed. Include the "not medical advice" disclaimer.

5. "Not medical advice" disclaimer must appear on every screen that could be construed as health guidance.

CONSTRAINTS:
- Keep it a single cohesive design language. Calm, clean, accessible - NOT generic purple-gradient-on-white.
- All new code in src/. Do not touch the build config beyond extending tailwind.config.js and adding fonts.
- No backend, no real auth provider - on-device localStorage is fine for this phase.
- TypeScript must type-check clean (npm run build runs tsc). ESLint must pass (npm run lint).
